# OctantCompass 法

> 固さ: 後から記録する層（[憲法の原則 10](../constitution.md#10-段階と文書の固さ)）。正本: 守る意味はこの文書、作りはコード。

## この文書の役割

[憲法](../constitution.md)と[契約](../contracts/README.md)の下で、OctantCompass（ゲームの外で動く推薦サーバー）の実装が守る意味だけを書きます。どう実装するか（モジュール、ファイルの形、名前）は書きません。ここに書いた意味を守る限り、実装は AI が自由に変えてよいものです（憲法の原則 9）。

- **上下の関係**: 憲法 → 契約 → この文書。この文書は憲法と契約を変えられません。ここにある決まりを守るために境界を越える必要が出たら、実装を止めてメンテナーに判断を求めます
- **書き方**: 1 つの決まりに、守ること、理由、出所を付けます。出所が「決定」のものはメンテナーの意図なので、変えるときは OctantSpecs の PR でメンテナーに理由を示します
- **実装契約を出所にしたもの**: 出所が「実装契約」の決まりは、OctantCompass を OctantPath・OctantVector から独立して作るための発注書だった OctantCompass 実装契約（2026-10-07 承認。2026-10-17 に退役し、公開していません）から引き継いだものです。括弧の中は、その文書の節の番号です
- **使い方と数値**: コマンド、ファイルの置き場所、設定の項目は [OctantCompass の README](https://github.com/BeatOctant/OctantCompass/blob/main/README.md) にあります。回数や時間などの数値は設定で変えられ、既定値は [defaults.json](https://github.com/BeatOctant/OctantCompass/blob/main/src/octantcompass/defaults.json) にだけあります（1.9）

## 1. 守る境界

**1.1 OctantVector の計算を再実装しない。** 距離、類似度、好み、実力、候補の評価を自分で計算しない。ベクトルや配布 DB のファイル（parquet、npy、マニフェストの中身）を直接読まない。DB について知ってよいのは、`open_db` が返す DB の `info()` の項目（[契約1 推薦側（OctantCompass → OctantVector）](../contracts/engine-runtime.md)）だけ。
理由: 推薦の計算は OctantVector が担う（憲法の原則 4）。出所: 実装契約（2 の 1）。

**1.2 第二の評価器を作らない。** `recommend` の結果を並べ替えない、点数を足さない、間引かない。応答の候補は `recommend` が返した順のまま返す。件数を絞るときは `recommend` に件数を渡す。候補が件数に足りなくても、足りないまま返す。理由（`reason`）は表示のために MOD へ渡すだけで、並べ替えや絞り込みに使わない。
理由: 憲法の原則 4・6。出所: 実装契約（2 の 2、4.2）。

**1.3 履歴は選り分けずに渡す。** その環境のキャッシュにあるすべての signal（`imported_play` と `recommendation` を含む）を、契約3（OctantPath ↔ OctantCompass）の `events` の形のまま、受け取った順に、要求のたびに `recommend` と `describe` に渡す。好意の判定、実力の推定、修飾付きのプレイや `restart` を使うかどうかは OctantVector が決める（[契約1 推薦側の履歴の signal の扱い](../contracts/engine-runtime.md#履歴の-signal-の扱い)）。好みや実力を OctantCompass の中で作ったり保存したりしない。
理由: signal をどう使うかは OctantVector の決めごと。出所: 実装契約（2 の 3、3）。毎回すべて渡すのは[推薦の定義](../plans/recommendation-definition.md)の Q5 の暫定の決定で、時間を測って確かめる。キャッシュが要るなら OctantVector の中で持つ。

**1.4 粒度を潰さない。** play は譜面（`hash` + `characteristic` + `difficulty`）の単位で受け取ったまま保存し、upvote・downvote・like・user_delete は `hash` の単位で保存する。play をマップ単位に丸めない。`characteristic`（プレイスタイル）を落とさない。旧版の `hash` は受け取ったまま保存する（現行版への置き換えは OctantVector がする）。
理由: 憲法の原則 1・2。出所: 実装契約（2 の 4）。

**1.5 ユーザー状態の正本を持たない。** signal、play history、推薦の設定の正本は OctantPath にある。OctantCompass が持つ履歴はキャッシュで、ファイルに書かず動いている間だけメモリに持ち、起動し直せば OctantPath が正本を丸ごと送り直して同じ状態に戻る（契約3 2.0。2026-10-22 決定）。推薦の数値は要求ごとに MOD から受け取った `params` を足し引きせずに使い、OctantCompass の中に推薦の設定（[憲法の原則 5](../constitution.md#5-octantpath-は-beat-saber-側とユーザー状態を担う)。どの手札をどこに出すか、件数、推薦の数値など）を持たない。手札の一覧と中の条件は推薦の設定ではない。OctantVector が配布 DB（なければ自分の既定の手札）から読んで返し、OctantCompass は契約1 推薦側の `presets` と `expand_preset` を呼んで中継するだけで、中身を組まない（[プリセットの 8 節](../plans/presets.md#8-手札の定義を配布-db-に移す2026-10-10)）。OctantPath の台帳（取得したマップの状態）の写しも持たない。出さないマップや譜面は要求ごとに MOD から受け取ったものを使う。
理由: 憲法の原則 4・5・7。出所: 決定（2026-10-06。ユーザー状態の正本を OctantPath に置く）、実装契約（2 の 5）。

**1.6 環境を混ぜない。** 履歴と session context は環境（トークン）ごとに分ける。ある環境の要求に、別の環境の履歴を使わない。同じトークンで別の正本（複製したゲームのフォルダ）がつないだときは、後につないだ正本の履歴に置き換わるだけで、見分けも混ぜもしない（2026-10-22 決定）。
理由: OctantPath の正本は環境ごとに分かれる（憲法の原則 4）。出所: 実装契約（2 の 6）。

**1.7 ゲームに依存しない。** Beat Saber のプロセス、class、MOD の内部 API に依存しない。ゲームのフォルダのファイルは読みも書きもしない。
理由: OctantPath と同じ端末で動くとは限らない（憲法の原則 4）。出所: 実装契約（2 の 7）。

**1.8 依存の向きを守る。** OctantPath を呼ばない（要求に答えるだけ）。OctantVector は契約1 推薦側（`octantvector.runtime`）の関数だけを呼び、生成側は呼ばない。`octantvector` を import するのは、OctantVector とつなぐ 1 つの部品だけにする。OctantVector の生成側の依存（音声モデル、GPU など）が入っていない環境で動くこと。
理由: 憲法の原則 8。出所: 実装契約（1、2 の 8）。

**1.9 数値は設定で変える。** OctantCompass 自身の動作の回数、時間、件数は、OctantCompass の設定ファイルか引数で変えられるようにする。既定値は同梱の [defaults.json](https://github.com/BeatOctant/OctantCompass/blob/main/src/octantcompass/defaults.json) にだけ置き、設定ファイルには利用者が変えた値だけを書く（読むときに書き戻さない）。推薦の数値は OctantCompass の設定に置かない。OctantPath の設定にあり、要求の `params` で届く。
理由: 既定値は 1 か所にだけ書く（[OctantSpecs の書き方](../README.md)）。出所: 実装契約（2 の 9、7）、OctantCompass #38。

**1.10 ユーザーデータを外に出さない。** 待ち受けは既定で 127.0.0.1 だけで、広げるのは設定で明示したときだけ。`/v1/health` と `/v1/pair` 以外は 127.0.0.1 でもトークンが要る（契約3（OctantPath ↔ OctantCompass））。トークンと合言葉はログに書かず、保存するのはトークンのハッシュだけ。管理画面のページは OctantCompass の窓が持ち、HTTP では配らない。窓が呼ぶ管理 API（`/manage/`）は 127.0.0.1 と ::1 からだけ受け付け、起動ごとの鍵を要る（2026-10-23。それまでは鍵なし、2026-10-13 決定）。鍵は持ち主だけが読めるファイルに置く。adb reverse では別の端末のアプリも 127.0.0.1 から届くため。要求の `Host` がこの PC の名前（127.0.0.1、localhost、::1）であること（DNS リバインディングを防ぐ）を確かめ、ブラウザがページから送るときに付ける `Origin` があれば断り、どちらも 403 にする（待ち受けを広げても、ほかの端末やブラウザのページからは使えない）。テストの固定データには実在のユーザーのプレイ記録や投票を入れない（`hash` は作った値を使う）。
理由: プレイの記録、投票、トークンは利用者のもので、外へ出るものは固める核（[憲法の 10](../constitution.md#10-段階と文書の固さ)）。出所: 実装契約（2 の 10）。

## 2. 履歴と session context

**2.1 signal は DB の状態に関わらず受け取る。** `loading` や `degraded` の間に届いた signal も捨てずにキャッシュに入れる。どの event を受け取り、どれを受け取らないかは契約3 のとおり（[OpenAPI](../contracts/mod-api.openapi.yaml) の `SignalsResponse`）。
理由（推測）: DB が使えないあいだも OctantPath の送信を止めず、使えるようになった最初の推薦から履歴を使うため。出所: 実装契約（4.2）。

**2.2 session context はキャッシュから作る派生物。** その環境のキャッシュした play から作り、保存はしなくてよい。保存するならキャッシュの一部として扱う。session context は難易度の狙いを決めるためだけに使い、OctantVector にはセッションを渡さない（OctantVector はセッションを知らない）。
理由: 正本は OctantPath の履歴（憲法の原則 4・7）。出所: 実装契約（4.3）。

**2.3 セッションはプレイの時刻の間隔だけで区切る。** play の `at` が、同じ環境の前の play から `params` の `sessionGapMinutes` 以上空いたら新しいセッションにする。最後の play から要求の時刻までがその時間以上空いたときも、要求は新しいセッションの最初（0 プレイ目）として扱う（[難易度合わせ](../plans/difficulty-fit.md)の「前のプレイの終わりから設定の時間以上空いたら、新しいセッションとして数え直す」）。ゲームの起動は区切りに使わない。
理由: 起動だけを繰り返してもプレイがなければ数は進まない。ゲームの起動を OctantCompass に知らせる道は契約3 にない。出所: 2026-10-12（暫定の扱いを正式にした）、実装契約（4.3）。

**2.4 何プレイ目かは play の数で数える。** `result` が `quit` と `restart` の play も 1 プレイに数える。`imported_play` は数えない。
理由: 難易度合わせの状況による調整は「セッションの中の位置」で測っている。出所: 実装契約（4.3）。

**2.5 `auto` の狙いは慣らしかふつうにする。** 難易度が `auto` のとき、今のセッションのプレイ数が `params` の `warmupPlays` に達していなければ `warmup`、それ以外は `normal` にする。`auto` では `challenge` を使わず、MOD が明示したときだけ使う。MOD が狙い（狙いの名前か、クリアできる見込みの目標）を明示したときは、そのまま渡し、状況による調整はかけない。`sessionGapMinutes` と `warmupPlays` は OctantCompass だけが使う `params` で、省かれたら[難易度合わせの設定](../plans/difficulty-fit.md#設定)の既定値を使う。狙いを譜面の距離に変えるのは OctantVector で、OctantCompass は距離を計算しない（推薦の定義の Q4）。
理由: `auto` に `challenge` を混ぜる割合は決めていない（難易度合わせの「難易度が合う枠の半分」の枠は MOD のもので、契約3 に出てこない）。出所: 2026-10-12（暫定の扱いを正式にした）、実装契約（3）。

## 3. 起動と終了

[契約6（つなぐ側 ↔ OctantCompass）](../contracts/launch.md)が、OctantCompass をいつ動かしておくかをこの文書に預けています。

**3.1 つなぐ側からは起動されない。** OctantPath の MOD や OctantPath Desktop は OctantCompass を起動しない。ログインしたときに起動して常駐する設定を OctantCompass が持ち、既定は切。
理由: PC を起動してすぐ Beat Saber をする人はまれ。出所: 決定（2026-10-13）。

**3.2 DB は使うあいだだけ持つ。** 常駐している間、DB（読み込むと 2GB ほど使う）を読み込んだままにしない。起動したとき（ログインで起動したときも）は読み込まない。ペアリングした環境からトークン付きの要求を受けたら（管理画面で手札の一覧を開いたときも）読み込みを始め、決まった時間（設定 `idle_minutes`）トークン付きの要求がなければ手放す。`idle_minutes` が 0 なら、起動時に読み込んで手放さない。手放している間の `/v1/health` は `loading` で、トークンのない要求では読み込みを始めない。
理由: 常駐しているだけでメモリを使い続けない。同じネットワークの誰でも読み込ませられないようにする（[契約6 の起動と常駐](../contracts/launch.md#起動と常駐)）。出所: 決定（2026-10-13）。

**3.3 2 つ目は起動しない。** 同じ置き場所で動いている OctantCompass（`/v1/health` に答える）がいれば、何もせず終了コード 0 で終わる。プロセスがない、または答えなければ、残っていた接続情報は古いものとして上書きする。
理由（推測）: 1 つの置き場所のペアリングとキャッシュを、2 つのプロセスで書かない。出所: 実装契約（4.4）。

**3.4 接続情報ファイルは OctantCompass 自身のもの。** 待ち受けているアドレスとポート、PID などを書くファイルは、多重起動の防止と `gui` のためだけのもので、契約の外にある（つなぐ側は読まない）。そのユーザーだけが読めるようにし、合言葉は入れない。SIGINT、SIGTERM、管理画面の停止で終わるときは、このファイルを消してから終わる。
理由: つなぐ側とはファイルを共有しない（契約6 2.0）。出所: 決定（2026-10-13）、実装契約（4.4）。

## 4. 管理画面

契約6 が、管理画面（OctantCompass の窓）の中身と管理 API（`/manage/`）をこの文書に預けています。画面の項目と API の形は OctantCompass のコードが正本です。

**4.1 管理画面は OctantCompass を管理するだけで、推薦を出さない。** 管理画面が持つのは、状態、DB の切り替えと取り込み、つないだ環境と取り消し、ペアリングの合言葉、手札の一覧（OctantVector が返したまま）、直近のログ、設定、停止と再起動。推薦の一覧や試し引きは持たない。契約3（OctantPath ↔ OctantCompass）の外にあり、守り方は 1.10 のとおり。
理由: 推薦を見せて選ばせるのは OctantPath（MOD と OctantPath Desktop）の役目。出所: 実装契約（1。OctantCompass 2026-10-11 の実装に合わせて記録）。

**4.2 管理画面の再起動は、プロセスを起こし直さない。** 同じプロセスの中で設定を読み直し、待ち受けだけを張り直す。DB、ペアリング、合言葉はそのまま。ポートが自動（0）なら今のポートを使い続ける。張り直せなければ前のアドレスとポートで答え続け、理由を画面に出す。ポートが変わるときは、新しいポートで答え始めて接続情報を書き換えてから古いポートを少しのあいだ残し、開いていた画面は新しいポートへ移る。
理由（推測）: 再起動のたびに DB を読み込み直さず、つないでいる OctantPath を切らないため。出所: 実装契約（4.4。OctantCompass 2026-10-12 の実装に合わせて記録）。

## 5. 環境とペアリング

[契約6 のペアリング](../contracts/launch.md#ペアリング)の、OctantCompass の側の決まりです。

**5.1 ペアリングは OctantCompass の正本で、キャッシュと分ける。** つないでよい環境の一覧とトークンは OctantCompass の正本。履歴のキャッシュとは別に保存し、キャッシュを消してもペアリングは残す。
理由: キャッシュは消えてよいもので、ペアリングは OctantPath から作り直せない（憲法の原則 7）。出所: 実装契約（5）。

**5.2 合言葉は短く、1 回だけ使える。** 同じ PC でも別の端末でも、管理画面か `pair code` で短い合言葉を作って表示する。有効な時間か失敗の上限（どちらも設定）を過ぎたら使えない。1 回使ったら無効にする。動いているサーバーと別のプロセスからも作れるよう、ペアリングの保存先を通して渡す。
理由: 人の操作なしにペアリングする道を持たない（契約6）。出所: 決定（2026-10-13。契約6 2.0）、実装契約（5）。

**5.3 ペアリングのたびに新しい環境にする。** 表示名は要求のものを記録する。同じ表示名でも別の環境として扱い、前の環境は取り消すまで残る。
理由（推測）: 表示名は環境を見分けるものではない。出所: 実装契約（5）。

**5.4 トークンは推測できず、ハッシュだけを保存する。** トークンは推測できない十分に長いランダムな文字列で、保存するのはハッシュだけ。`Authorization: Bearer <トークン>` で受け取る。期限はなく、取り消すまで使える（契約3）。
理由（推測）: 保存先を読まれても、つないでいる環境になりすませないようにする。出所: 実装契約（5）。

**5.5 取り消したら消す。** 取り消した環境は一覧から消し、その環境のキャッシュも消す。取り消したトークンの要求は 401。無効にして残す形は持たない。
理由: 残しても働きがなく、元に戻す操作もない。出所: 2026-10-13。

## 6. DB の更新

[契約5（OctantHarvest → 配布先 → OctantCompass）](../contracts/distribution.md)の、受け取る側の決まりです。

**6.1 DB のファイルを組み立てず、署名を扱わない。** 何を取るかは `plan_update`、確かめて新しいフォルダに書くのは `apply_update` に任せる（契約1 推薦側）。OctantCompass がするのは、索引と、`plan_update` が挙げたファイルの取得と、`open_db` が通ってからの切り替えだけ。署名を確かめるのは `apply_update` で、OctantCompass は自分の設定（信頼する鍵と、署名のない版を受け入れるか）を `trust` として渡すだけ（[契約5 の署名](../contracts/distribution.md#署名)）。
理由: DB の中身は OctantVector の中で閉じる（1.1）。出所: 実装契約（6、7）。

**6.2 確かめてから切り替え、失敗したら今の版を使い続ける。** 新しい版は別のフォルダに書き、`open_db` が通ってから参照を入れ替える。失敗したら手元の版を使い続ける。`plan_update` が `VersionError` を出したら手元の版を使い、`/v1/health` に `update.reason: index_unsupported` を出す。
理由（推測）: 更新の失敗で推薦を止めない。出所: 契約5、実装契約（3、6）。

**6.3 索引からの取り込みは、人が頼んだときだけ。** 索引の URL（https だけ）を設定するまで自動の更新は切り、取り込むのは人が頼んだとき（`db update`、管理画面）だけ。決まった間隔での自動の確認はまだない。取得の決まり（https だけ、大きさの上限、User-Agent）は契約5 のとおり。
理由（推測）: 配布先と索引は公開（リリース）から使う（[契約5 の非公開（探求中）の扱い](../contracts/distribution.md#非公開探求中の扱い)）。出所: 実装契約（6。OctantCompass 2026-10-11 の実装に合わせて記録）。

**6.4 手渡しの DB はファイルから取り込み、手元のフォルダへの切り替えは署名を通らない。** 公開（Dev 版）で手渡しする DB は、全量の tar 1 つ（`<dbVersion>.full.tar`）を、索引を通さずに取り込む（`db import`、管理画面の「ファイルから取り込む」）。確かめて展開するのは OctantVector の `import_archive` で、署名も `apply_update` と同じに確かめる（6.5 が当てはまる）。展開先はデータフォルダの `dbs/` で、名前は tar のファイル名から付ける（中身は見ない。6.1）。そのあとは 6.2 のとおり。手元で作った DB は、ローカルのフォルダを指定して切り替えるコマンド（`db switch`）か管理画面で使う。この道は `apply_update` を通らず、`open_db` は署名を確かめないので、署名の警告も出ない。
理由: 非公開（探求中）と Dev 版の DB は索引に載らない（契約5 の非公開（探求中）の扱い）。手渡しを 1 ファイルにすると、渡すのも置くのも楽になり、手渡しでも作者が分かる（2026-10-17）。出所: 実装契約（6）、OctantCompass #44。

**6.5 署名の警告は出して、その版を使う。** `apply_update` か `import_archive` が `SignatureWarning` を出してもその版を使い、警告は管理画面の取り込みの結果とログ、`db update` と `db import` の出力に出す。
理由: 署名は作者を示すもので、合わない版を止めない（契約5 の署名、2026-10-11 決定）。出所: OctantCompass #38。
