> 固さ: 後から記録する層（[憲法の原則 10](../constitution.md#10-段階と文書の固さ)）。ただし 5 節（ユーザーのデータ）のうちプレイの記録を壊さないことは固める核です。正本: 守る意味はこの文書、作りはコード。

## この文書の役割

[憲法](../constitution.md)と[契約](../contracts/README.md)の下で、OctantPath（ゲーム内の MOD）の実装が守る意味だけを書きます。どう実装するか（クラス、台帳のファイルの形、使う API、名前）は書きません。ここに書いた意味を守る限り、実装は AI が自由に変えてよいものです（憲法の原則 9）。

- **上下の関係**: 憲法 → 契約 → この文書。この文書は憲法と契約を変えられません。ここにある決まりを守るために境界を越える必要が出たら、実装を止めてメンテナーに判断を求めます
- **書き方**: 1 つの決まりに、守ること、理由、出所を付けます。出所が「決定」のものはメンテナーの意図なので、変えるときは OctantSpecs の PR でメンテナーに理由を示します
- **旧実装を出所にしたもの**: 出所が「旧実装」の決まりは、別の計画で作って止めた旧 OctantPath（手元に残している BeatLegacy。OctantSpecs には入れていない）で起きたこと、確かめたことから取った意味です。括弧の中の記号（IDENTITY-01 など）は、旧実装（BeatLegacy）の不変条件の番号です。旧実装のクラス、台帳の形、数値は引き継ぎません
- **旧実装からの教訓**: 法には入らない、進め方の教訓です。
  - 旧実装は MOD の中に推薦（好みと実力の推定、候補の探索、外部サービスでの照合）を作り込み、その検証の研究に入り込んで、「推薦が出て、遊んで、残す・消す」が一度も通りませんでした。推薦の計算は OctantVector の責務で、OctantPath は表示と観測と入れ替えだけを持ちます（憲法の原則 3・6）。そのため、実装の各段階でゲームの中で一周させてから次へ進みます
  - 旧実装はプレイの開始、結果、やり直しを Harmony のパッチで取っていました（開始は `SinglePlayerLevelSelectionFlowCoordinator.StartLevel` の Prefix、結果は `SoloFreePlayFlowCoordinator.ProcessLevelCompletionResultsAfterLevelDidFinish` の Postfix、やり直しは `StandardLevelRestartController.RestartLevel` の Prefix）。途中終了の観測は確かめていません。U1 を決めるときの手がかりで、パッチを使ってよいという意味ではありません
  - BSML: Mod Settings から戻るとメニューボタンの置き場所が作り直されるので、古い参照を外して登録し直す必要がありました
- **実装の構想との分け方**: 部品の分け方は [OctantPath の実装構想](../plans/octantpath-implementation.md)にあります。構想とこの文書が食い違うときは、この文書が優先です
- **数値**: 上限や回数などの数値は、この文書では決めません。設定 JSON で変えられるようにし、既定値は OctantPath の [`src/OctantPath.Core/Settings/defaults.json`](https://github.com/BeatOctant/OctantPath/blob/main/src/OctantPath.Core/Settings/defaults.json) にだけ置きます（[文書の決まり](../CONTRIBUTING.md#値の正本)）

## 1. 識別

**1.1 map key、版の hash、譜面を取り違えない。** マップは BeatSaver の版の hash で、譜面は hash + `characteristic` + `difficulty` で特定する（契約3（OctantPath ↔ OctantCompass）の共通ルール）。map key、ゲームの level ID、フォルダ名、曲名の一致を、版や譜面の一致の代わりにしない。プレイの結果は、マップではなく譜面に結び付ける。
理由: 同じ map key に別の版があり、同じマップに別の譜面がある（憲法の原則 1・2）。出所: 決定（2026-10-01）、旧実装（IDENTITY-01、DOWNLOAD-01）。

**1.2 hash は形式を確かめ、正規化してから比べる。** 大文字と小文字の違いで別のマップと判断しない。
理由: 出所によって大文字と小文字が混ざる。出所: 旧実装（IDENTITY-02）。

**1.3 一意に決まらないものは選ばない。** 同じ hash のマップが複数ある、台帳の 1 件が複数のフォルダに当たるなど、対象が 1 つに決まらないときは、どれか 1 つを選んで削除や解決を進めない。
理由: 間違ったほうを消すと取り返せない。出所: 旧実装（DUPLICATE-01）。

## 2. 取得と設置

**2.1 頼んだ版の中身だけを入れる。** ダウンロードは期待する hash の版を選び、同じ map key の別の版や先頭の版で代用しない。展開した中身から hash を計算して期待する hash と照合し、合わないもの、ファイルが欠けているものは入れない。HTTP の応答や ZIP が正常なだけでは、取得できたことにしない。
BeatSaver から取る zip は、API が返した `downloadURL` が https の beatsaver.com とその下のときだけ取る（転送された先も同じ。OctantPath #32）。
理由: 推薦された譜面と違うものを遊ばせ、違うものの記録を送ることになる。出所: 旧実装（DOWNLOAD-01・02）。hash の計算は、ZIP 全体ではなく Info.dat とそれが指すファイルを決まった順に連結した SHA-1 で、Info.dat の形式が v4 なら音源・譜面・ライティングのファイルも含む（旧実装のコードと、v4 のマップの実機での取得で確認。旧実装の Python 版は v4 の分を漏らしていた）。

**2.2 受け取る量と展開する量に上限を持つ。** 受信量、展開後の合計、ZIP の entry 数（フォルダの entry も数える）に上限を設ける。途中で失敗・中止したものを完成品として扱わない。
理由: 壊れた ZIP や悪意のある ZIP でディスクを埋めさせない。出所: 旧実装（DOWNLOAD-03、ARCHIVE-02）。

**2.3 ZIP の中の名前を信用しない。** entry 名や Info.dat が指すファイル名が、展開先とマップのフォルダの外を指さないことを確かめてから使う（`..`、絶対パスなど）。マップの根が 1 つに決まらない ZIP、必要なファイルが欠けた ZIP は、どれかを選んで入れずに拒否する。
理由: 外部から来た名前でゲームのフォルダの外を書き換えさせない。出所: 旧実装（ARCHIVE-01・03）。

**2.4 検証が済むまで、完成したマップとして見せない。** 展開と検証は作業用の場所で行い、通ったものだけを置き場所に移す。移すときに途中の状態が見えないよう、同じファイルシステムの中で入れ替える。置き場所にすでに何かあれば上書きしない。失敗して片付けるのは、自分がその処理で作ったものだけにする。
理由: 途中まで入ったマップをゲームや SongCore に読ませない。元からあるマップを巻き込まない。出所: 旧実装（INSTALL-01〜03）。

**2.5 置いたことと遊べることを分ける。** ファイルを置いたあと、SongCore の読み込みが終わり、その譜面がゲームの中で解決できたことを確かめてから「取得済み」として扱う（契約3（OctantPath ↔ OctantCompass）の `recommendation` の `downloaded` もこの後に送る）。再読み込みを頼んだだけでは成功にしない。
理由: 置いただけでは選曲画面に出ないことがある。出所: 旧実装（REFRESH-01）。

**2.6 ゲームが参照しているものを、同時に書き換えない。** マップのファイル、SongCore の読み込み、一時的に登録した表示（パックなど）を、選曲やプレイの最中に変えない。取り消しを頼んでも、実際に書き換えている処理が止まるまでは止まったとみなさない。一時的に登録したものを外すときは、自分が登録したものだけを外す。
理由: 選曲画面やプレイ中の参照が壊れる。出所: 旧実装（REFRESH-02、PACK-01）、構想（ゲームプレイ中は通信もファイル操作もしない）。

**2.7 自動ダウンロードを切ったら、新しく取らない。** 切る前の設定を、切ったあとの取得に使わない。切ったことを、すでに入れたマップを消す理由にしない。
理由: ユーザーの指定より前の状態で動かない。出所: 旧実装（CONSENT-01）、決定（2026-10-01。自動ダウンロードは設定で切れる）。

**2.8 取得元の設定を守り、取得元を書き換えない。** zip の取得元をローカルのフォルダにしているあいだは、そこにないマップを BeatSaver から取らずに飛ばし、そのマップは今回の取得では実行できないものとして扱う（推薦の順位は変えない。憲法の原則 6）。取得元のフォルダは読むだけで、書き込まず、消さない。ローカルから入れたマップも、2.1〜2.5 の検証と設置、3 の所有と削除は BeatSaver から取ったものと同じに扱い、消すのは設置した側だけにする。
理由: 試験のあいだ BeatSaver に負担をかけない。取得元は OctantPath のものではない（3.1）。出所: 決定（2026-10-08。試験段階は取得元をローカルにする）。

## 3. 所有と削除

**3.1 自分で入れた証拠があるものだけを自分のものとする。** 手元にある、SongCore が読み込んでいる、プレイリストに入っている、専用フォルダにある、だけでは OctantPath のものとしない。所有は、2.1〜2.5 の検証と設置が済んだあとにだけ記録する。取得の予定、ダウンロードの開始、設置の失敗は所有の証拠ではない。
理由: 元からあるマップを消さないため。出所: 旧実装（OWNERSHIP-01・02）、構想の「既存のマップとの区別」。

**3.2 所有の記録が読めないときは、所有を推測しない。** 記録が欠けている、壊れている、古い形式である、曖昧であるときは、そのマップを自分のものとして扱わず、削除もしない。
理由: 推測で削除の権限を得ると、元からあるマップを消し得る。出所: 旧実装（OWNERSHIP-03）、構想（台帳が壊れたら専用フォルダの中身も自動削除しない）。

**3.3 消す直前に、今の中身が記録と同じか確かめる。** 削除の対象は、所有の記録があり、許された置き場所の中にあり、今のフォルダの中身の hash が記録と一致するものに限る。中身が変わっていたら消さない。
理由: 記録したあとにユーザーが入れ替えたり、別のマップが同じ名前で入ったりする。出所: 旧実装（DELETE-01）。

**3.4 守る情報が読めないときは、削除を止める。** 所有の記録、設定、お気に入り、投票の記録のうち、必要なものが読めないときは「守るものはない」とみなさず、削除をまとめて止める。投票の MOD が入っていないことと、入っているのに記録が読めないことは別に扱う。
理由: 読めないことを「保護なし」と読むと、守るべきマップを消す。出所: 旧実装（DELETE-02）。

**3.5 好意の印があるマップは消さない。** お気に入りか Upvote があるマップは、自動削除の候補から外す。この印は所有を新しく与えるものではない（所有していないマップはもともと消さない）。
理由: 好きだと示したマップを消さない。出所: 構想の「残す」の判定（2026-10-01 決定）、旧実装（DELETE-03）。

**3.6 消すことに失敗しても、戻せる状態を失わない。** 削除の途中で失敗して戻す必要が出たときに、戻すための写しを失わない。戻せない食い違いが起きたら、残りの削除を続けない。
理由: 1 件の失敗を、複数のマップの消失に広げない。出所: 旧実装（DELETE-05）。

**3.7 派生した表示を所有の証拠にしない。他人のファイルを上書きしない。** 専用プレイリストなどは台帳から作る表示で、所有の証拠にはしない。書き出し先に、OctantPath が作った印のないファイルがあれば上書きしない。
理由: 名前が似ているだけのユーザーのプレイリストを壊さない。出所: 旧実装（PROJECTION-01）。

## 4. プレイの観測

**4.1 結果の種類を区別し、読み替えない。** clear、fail、quit、restart を区別して記録する（値は契約3（OctantPath ↔ OctantCompass）の `play`）。中断の操作を、残った最後の状態から clear や fail に読み替えない。restart は前の試行の clear ではなく、やり直した試行の結果は新しい試行として記録する。
理由: quit と restart は好みかどうか分からず、好みの判定では数えない（契約1（OctantCompass・OctantHarvest → OctantVector））。混ぜると判定がずれる。出所: 決定（2026-10-01、2026-10-06）、旧実装（SESSION-01・04）。

**4.2 開始と結果を別の観測として扱う。** 開始の要求、実際の開始、終わった結果は別のものとして扱う。開始の観測だけから、結果やプレイ時間を作らない。
理由: 開始を頼んでも、読み込みに失敗したり、すぐ戻ったりする。出所: 旧実装（SESSION-02）。

**4.3 結果は、同じ試行の同じ譜面に結び付ける。** 別の譜面の結果や古い通知を、今の試行の結果にしない。同じ結果を 2 回数えない。
理由: 譜面の取り違えと二重計上は、そのまま好みと実力の推定に入る。出所: 旧実装（SESSION-03）。

**4.4 分からないことは分からないまま送る。** 修飾（速度、ノーフェイルなど）やスコアが取れなかったら、標準の条件で遊んだとみなして埋めない。開始だけ記録されて結果がないもの（ゲームの異常終了など）は、結果不明として扱い、quit や fail に変えない。
理由: 推測で埋めた値は、本物の観測と見分けられなくなる。出所: 旧実装（RESULT-01、RECOVERY-03）、契約3（OctantPath ↔ OctantCompass。MOD は観測できたものだけを送ってよい）。

**4.5 観測できないときは、観測をやめる。ゲームを壊さない。** ゲームの版や観測に使う部品が想定と違うときは、観測を止めて記録を作らない。観測の失敗で、選曲、プレイ、結果画面の普段の操作を妨げない。観測が止まっても、推薦とダウンロードは動き続ける。
理由: ゲームの更新で観測が壊れることがある。そのときの失敗は「記録が止まる」に留める。出所: 旧実装（OBSERVER-01）、構想のリスク（シグナルの観測が壊れても推薦とダウンロードは動くようにする）。

## 5. ユーザーのデータ

OctantPath は環境ごとにユーザーの signal、play history、推薦の設定の正本を持ちます（憲法の原則 5・7）。

**5.1 ユーザーが明示的に選んだときを除き、元のファイルを書き換えない。** 観測や取り込みのために、PlayerData、お気に入り、投票の記録、スコア、リプレイ、他の MOD やユーザーのプレイリストを書き換えない。書き換えてよいのは、ユーザーが設定と操作の両方で選んだときだけで、そのときもファイルを直接書かず、ゲームや持ち主の MOD の操作を通す（ユーザーが自分で押したのと同じ結果にする）。過去の記録にさかのぼって書き換えない。正本に要らない生のデータ（プロファイル全体、スコアの全履歴など）を写して持たない。
理由: ユーザーのデータで、壊すと取り返せない。好意ボタンからお気に入りや Upvote を付ける設定（2026-10-29）は、ユーザーが選んだ 1 押しの結果なのでこの中に入る。出所: 旧実装（USERDATA-01）。

**5.2 読めないことを、否定の評価にしない。** 記録がない、壊れている、値が分からない、手元のマップに解決できないことを、嫌いの印として扱わない。解決できない ID を、似た別のマップや同じアーティストに付け替えない。
理由: 曖昧なシグナルを負例にしない（[OctantVector 法](../octantvector/law.md) 4.2 と同じ考え方）。出所: 旧実装（FEEDBACK-01）。

**5.3 マップが消えても、そのマップへの印は消さない。** 手元のマップを消しても、hash で対象が分かる投票やお気に入りを「なし」に書き換えない。同じマップへの複数の印は、種類と対象を保ったまま持つ。
理由: 消したマップへの Downvote は、同じマップを再び推薦させないための情報になる。出所: 旧実装（FEEDBACK-02）。

**5.4 導入前の記録から、ないことを作らない。** 取り込む PlayerData の行から、元にない時刻、修飾、結果の内訳、失敗を作らない。`validScore` が偽であることだけを失敗の印にしない。
理由: PlayerData の行は 1 回ずつのプレイの記録ではない。出所: 旧実装（RESULT-02）、[OctantVector 法](../octantvector/law.md) 4.1 の好意の判定（導入前の回数は `imported_play` としてだけ使う）。

**5.5 正しい状態を、壊れた状態で置き換えない。** 正本や台帳を書き換えるときは、途中で失敗しても前の正しい状態が残るようにする。写しも壊れていたら、正しい状態を作り上げず、読めなかったことを示す。前のプロセスが残した「処理中」の印を、今も処理が続いている事実として扱わない。
理由: 正本は OctantPath にしかなく、OctantCompass のキャッシュは OctantPath から作り直す（憲法の原則 7）。出所: 旧実装（RECOVERY-01・02）。
