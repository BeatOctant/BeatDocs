## この文書の役割

[憲法](../constitution.md)と[契約](../contracts/README.md)の下で、OctantVector の実装が守る意味だけを書きます。どう実装するか（アルゴリズム、ファイルの形、関数やモジュールの名前）は書きません。ここに書いた意味を守る限り、実装は AI が自由に変えてよいものです（憲法の原則 9）。

- **上下の関係**: 憲法 → 契約 → この文書。この文書は憲法と契約を変えられません。ここにある決まりを守るために境界を越える必要が出たら、実装を止めてメンテナーに判断を求めます
- **書き方**: 1 つの決まりに、守ること、理由、出所を付けます。出所が「決定」のものはメンテナーの意図なので、変えるときは OctantSpecs の PR でメンテナーに理由を示します。出所が実験や実データのものは、新しい実験で覆ったら同じく PR で直します
- **実装の説明との分け方**: いまの実装がどうなっているかは [design.md](design.md)、[encoders.md](encoders.md)、[config.md](config.md) にあります。実装がこの文書と違うときは実装の方を直すか、[open.md の OctantVector](../open.md#octantvector) に書いてメンテナーの判断を待ちます。実装が先にあることを理由に、この文書を実装に合わせて書き換えません
- **対象外**: 評価・実験のコマンドなどの開発補助ツールは、憲法の原則 3〜8 を変えない限り、この文書の 1〜4 に従わなくてよい（憲法の「この文書の役割」）。ただし 4.3 は開発補助ツールにも効きます

## 1. 識別と粒度

**1.1 値は版と譜面に結び付ける。** ベクトル、検索結果、好みと実力の入力はすべて BeatSaver の version hash で結び、譜面の値は version hash + `characteristic` + `difficulty` で結ぶ。map key は表示にだけ使う。
理由: マップの取得にそのまま使える値で、版ごとに中身が決まるから。出所: 決定（2026-10-01、2026-10-02 の決定 A）。

**1.2 旧版の問い合わせは現行版に置き換え、置き換えたことを返す。** 譜面の問い合わせでは、現行版の同じ `characteristic` と `difficulty` を使う。
理由: 配布物には現行版しか入らない。出所: 決定（2026-10-02 の決定 B）。実装で分かったこと: 新しい版では同じ名前の譜面が作り直されていることがあり、置き換えた譜面は旧版の譜面と同じものとは限らない（OctantVector #14）。置き換えたことを返すのは、呼ぶ側がこの違いを知れるようにするため。

**1.3 譜面から作った特徴は譜面の単位で持つ。** 譜面から作った値を版の単位にまとめて（最難の譜面で代表させる、平均するなど）配布物や推薦に使わない。
理由: 同じマップの譜面ごとの違いが消える（憲法の原則 1・2）。出所: 憲法、OctantVector #14。開発補助ツールの版単位の実験で代表させるのは構わない。

**1.4 プレイスタイルが違う譜面どうしは比べない。** 特徴の類似度も、実力からの距離も、同じプレイスタイルの譜面の中でだけ測る。あるプレイスタイルの記録から作った実力を別のプレイスタイルの譜面に使うのは、それでよいと実験で確かめた場合だけ。
理由: 特徴の計算方法も、ユーザーの得意・不得意も違い得る（憲法の原則 2）。出所: 憲法。いまのスイングシミュレーションは Standard 用なので、ほかのプレイスタイルの譜面には `swing_*` の値がない。

**1.5 同じ hash の中身は変わらないものとして扱う。** 同じ hash で中身の違う zip が来たら、その zip は使わずに記録する。
理由: 版の中身が変わらない前提で、一度計算した値を使い続けるから。出所: 計画（2026-10-02）。

**1.6 譜面の難易度の表記ゆれは、カタログの書き方にそろえる。** 譜面の行を DB の譜面表（カタログ）に合わせるとき、`normal`、`Expert+` などの表記ゆれをカタログの書き方にそろえる。難易度そのものが違う譜面は入れず、件数と譜面をログに出す。
理由: 表記の違いだけで譜面を落とさず、違う譜面を同じものとして混ぜないため。出所: 決定（2026-10-08）。

## 2. 値の意味と版

**2.1 値は作った版と一緒に持ち、版の違う値どうしは比べない。** 1 つの値の意味は、エンコーダの定義（`id@version` と指紋）、外部データの定義、座標系（校正）、配布物の版で決まる。どれかが違う値どうしで類似度を測らない。
理由: 同じ数値でも作った版が違えば別のものになる。出所: 計画（2026-10-02）。層ごとの版の付け方は [design.md の値の版](design.md#値の版)にある。

**2.2 定義が変わったら版を上げる。** 値が変わり得る変更（パラメータ、モデル、学習済みファイル、元のビュー、前処理）をしたのに版が同じなら、計算を止める。実行環境（ライブラリの版）の違いは、決まった少数のマップで値が許容値を超えて変わったときに版を上げる。
理由: 版を上げ忘れると、違う意味の値が同じ版として混ざる。出所: 計画（2026-10-02）、OctantVector #4。

**2.3 座標系は固定し、全量でだけ作り直す。** 差分で足した行も、前からある行と同じ座標系に置く。座標系を作り直すのは、ずれが設定の閾値を超えたときの全量だけ。ビューを足すときは、ほかのビューの座標系を動かさない。
理由: マップが増えるたびに既存のマップの値が動くと、差分で配れない。出所: 決定（2026-10-02）。

**2.4 「前の全量 + 差分」と「新しい全量」は同じ中身にする。**
理由: 利用者がどちらの道で更新しても同じ推薦になるようにする。出所: 計画（2026-10-02）、OctantVector #9。

## 3. 検索と推薦の計算

**3.1 欠けたビューで点を稼がせない。** 複数のビューを重み付きで合わせるとき、片方にしかないビューはそのビューの類似度を 0 として数え、重みを割り直さない。持っているビューの重みが設定の下限に満たない行は候補に出さない。履歴の側（好意的なマップや起点の譜面）にそのビューのベクトルが 1 つもないときは、そのビューをその回の計算から外す。全候補が同じだけ欠けるので、候補を比べる意味がないため。
理由: 重みを割り直すと、共有するビューが少ない組（メタ情報だけの組など）が軽いビューの一致だけで上位に来た。出所: 決定（2026-10-03）。開発用の PC の実データの検索で見つかり、OctantVector #13 で直した。履歴の側の扱いは決定（2026-10-05）。

**3.2 曲名を特徴にしない。** 曲名、アーティスト名、動画のタイトルは、表示と記録の照合にだけ使い、類似度に使わない。
理由: 名前が似ていても曲や譜面が似ているとは限らず、名前の一致に推薦が引きずられる。出所: 設計方針（2026-10-01）。
意図の補足（2026-10-20）: 曲名だけをキーにすると、同じ曲名の別の曲、誤記、表記の揺れで見当外れの検索になる。これを防ぐための決まりで、名前の文字列をキーや近さに使わないことが要点。カバー画像の埋め込み（`siglip_cover`）は画像の中の文字も拾い得るが、文字列をキーにはしないので 3.2 の対象外とし、効き方は [open.md の V10](../open.md#octantvector) で見る。
改定（2026-10-11 承認、OctantSpecs #83）: ただし、アーティスト名を外部の ID（MusicBrainz のアーティスト ID）に照合し、その ID に結びついた聴取行動からの近さ（ListenBrainz の似たアーティスト）は類似度に使ってよい。名前の文字列どうしの近さは使わない。理由: ここでいう「似ている曲」は同じアーティストと近いアーティストの曲で、音だけでは取れなかった（[実験ログの近いアーティストの元データ](experiments.md#近いアーティストの元データ2026-10-11)）。名前の文字列を比べないので、3.2 の理由は当たらない。

**3.3 難しさは得意な譜面からの距離で測る。** 難しさを 1 本の数値や Easy〜Expert+ の名前、マッパーが付けた難易度名で決めない。狙い（ふつう・挑戦・慣らし、または「クリアできる見込み」の目標）から距離への変換は OctantVector がし、尺度と名前ごとの既定値も OctantVector が持つ（契約1（OctantCompass・OctantHarvest → OctantVector））。
理由: 人によって苦手な向きが違い、難易度名は作風で付けられることがある。出所: 決定（2026-10-03、[difficulty-fit.md](../plans/difficulty-fit.md)。狙いの渡し方は 2026-10-04 の[推薦の定義](../plans/recommendation-definition.md)の Q4）。

**3.4 同じ曲・同じアーティストの Map で一覧を埋めない。** 同じ曲の Map は推薦の一覧に既定で 1 つ（`params` の `mapsPerSong`）、同じアーティストの Map は既定で 3 つ（`params` の `mapsPerArtist`）まで入れる。どれを残すかは、その回の順位で上のもの（譜面の好みと難しさの合い方を含む）。
- 同じ曲かは音楽のビューの近さで見分ける。両方のマップにアーティスト ID（契約2（DB 生成 ↔ 推薦コア）の関係のビュー `listenbrainz_artists@<YYYYMMDD>`（役割 `artist`））があるときは、ID の組が同じことも要る。カバーと原曲（別のアーティストが歌った同じ曲）を、別の曲として残すため
- 同じアーティストかは、アーティスト ID の組が全部一致するかで見分ける。共作（A と B）は A だけの Map とは別のアーティストとして数える。ID のない Map は同じアーティストの上限を受けない
- 曲名とアーティスト名の文字列は使わない（3.2）

理由: 音声のビューは同じ曲の Map をほぼ同じベクトルにするので、有名な曲を起点や好意にすると、上位が同じ曲の別の Map で埋まった。近いアーティストを近さに入れると、上限がなければ同じアーティストの曲が上位を埋めた（上限なしで上位 10 件の 35%）。最初のアーティスト ID だけで比べると、「Doja Cat と Rainych」のカバーと Doja Cat の原曲が同じ曲として 1 つにまとまった。出所: 同じ曲は報告と決定（2026-10-08。間引くのは順位を付ける OctantVector で、OctantCompass ではない）。同じアーティストの上限 3 とアーティストの組で比べることは決定（2026-10-12、[決まったことの近いアーティスト](../decisions.md#近いアーティスト)）。

## 4. ユーザーのデータ

**4.1 好意の判定。** 次の決まりで、履歴の signal から好意的なマップを決める。OctantCompass は signal を選り分けずに渡し、判定はここでする（[契約1（OctantCompass・OctantHarvest → OctantVector）](../contracts/engine-runtime.md)）。
- プレイ回数に数えるのは、クリアとミスによる失敗（fail）。途中終了（quit）とやり直し（restart）は数えない
- 一度でもクリアしたマップのうち、お気に入り（いいね）か Upvote のどちらかがあるもの、または「クリアした後に、別の日にまた遊んだ」ものを好意的とみなす。お気に入りと Upvote は、片方だけでも両方でも同じ意味として扱う
- まだクリアしていないマップに付いたお気に入りか Upvote（片方でも両方でも）は、好意ではなく「目標」として扱う。好みの基準には入れず、腕前が追いついた頃にもう一度出すなど、挑戦の推薦に使う。あとでクリアすれば、上の好意の決まりで判定する。使い方: 挑戦の狙い（`difficulty: challenge`）では目標を既知の除外から外し、ほかの候補と同じに好みと許容幅で選ぶ（目標を優先はしない）。実力を推定できたプレイスタイルの譜面だけ。ユーザーが削除した目標は、0.5.0 ではほかの既知のマップと同じに除いたまま（推測。[open.md の推薦のその後](../open.md#推薦のその後)の決定を待つ）（OctantVector 0.5.0、#54）
- クリアしないまま繰り返し遊んだマップ（クリアと失敗の合計が多くても）は、好意とみなさない。「挑戦中」として、難しさの推定にだけ使う
- お気に入りは、同じマップの `like` と `like_removed` のうち最後のものだけが効く。`like_removed` はお気に入りの印がなくなっただけで、否定の材料には使わない（否定は `downvote`）。投票も同じマップの最後の `upvote` か `downvote` だけが効く
- 上に当たらないプレイ（1 回きりのクリア、失敗や途中終了を含む）、推薦のその後の出来事（表示、ダウンロード、選択）だけでは、好みの推定に使わない
- OctantPath を入れる前のゲームの記録（`PlayerData` のプレイ回数、途中終了を含む）は、OctantPath が初回の取り込みで作った `imported_play` としてだけ受け取る。結果も日付も分からないので、それだけでは好意にも目標にもならない。`cleared` が真のもの（PlayerData にスコアがある譜面）は、自分の素のクリアで埋まらない分だけ、実力の得意な譜面の枠を埋める（プレイ回数の多いものから。日付がないため）。自分のクリアと合わせて `minClears` に数えるが、クリアできる見込みの曲線と苦手な方向には使わない（失敗が取り込めないため。2026-10-24、[難易度合わせ](../plans/difficulty-fit.md)の 6）。そのマップに `play` がないときだけ、譜面のビューの基準に使う
- ユーザーによる削除（`user_delete`）は、その Map を推薦に出にくくするだけにする。曲の好みの否定には使わない（消した理由が、譜面が嫌い、判別できる腕前でなかった、楽曲が嫌い、のどれか分からないため。2026-10-10 決定）

理由: 開発に使った記録では、プレイ後に良かったと思えば Upvote を、付け忘れたらとりあえずお気に入りを付けていたので、どちらか一方で好意の表明になる。未クリアの繰り返しは、悔しくて挑んでいる場合が多い（Spike の F11 で、旧ルールの好意 146 マップのうち 28 が未クリアの繰り返しで、その Upvote は 41 中 3。その時の腕前よりずっと難しい譜面だった）。クリアした後に日を空けて戻ってくることが「また遊びたい」の印になる。「できなかったが、できるようになりたい」と思ってお気に入りを付けることもあり、未クリアのお気に入り（Spike の F13 で 23 マップ）は腕前よりずっと難しい側に寄っていた。好きから外すと、好きと譜面の特徴の関係がはっきりした。途中終了は理由が分からない。出所: 決定（2026-10-10。未クリアの印を目標にすることも同日。それまでの「プレイ回数 N 回以上」は 2026-10-01 の決定）。導入前の記録の扱いは決定（2026-10-05）。`like_removed` の扱いは決定（2026-10-07）。`imported_play` を譜面のビューの基準に使うことは決定（2026-10-08）。

**4.2 曖昧なシグナルを負例にしない。** 途中終了、N 回未満のプレイ（1 回の失敗を含む）、未プレイ、入れただけのマップは「ラベルなし」として扱い、嫌いとみなさない。
理由: 遊ばなかった理由が好みとは限らない。実験では、途中終了・失敗したマップと好きなマップの違いのほとんどは難易度だった（[exp05](experiments.md)）。出所: 設計方針（2026-10-01）。

**4.3 ユーザーのデータを持ち出さない。** 開発補助ツールは指定されたパスを読むだけで、プレイ記録、投票、視聴履歴をリポジトリにも外部にも出さない。テストの固定データには実在のユーザーの記録を入れない。
理由: 個人データだから。出所: 設計方針（2026-10-01）。

**4.4 1 人分のデータで全員の既定値を決めない。** 既定値の選び方と個人化の強さは [personal-data-overfitting.md](../plans/personal-data-overfitting.md) に従う。
理由: これまでの評価はほとんど 1 人分の記録で行った。出所: 決定（2026-10-03）。

## 5. 構成

**5.1 推薦側は生成側に依存しない。** OctantCompass から呼ばれる推薦側（契約1（OctantCompass・OctantHarvest → OctantVector）の関数）は、配布物の形式だけを生成側と共有し、生成側のコードや音声モデル・GPU などの依存なしで読み込めるようにする。
理由: 利用者の PC には生成側の依存を入れない。配布 DB は別系統（憲法の原則 8）。出所: OctantVector #15（パッケージの分け方は [design.md](design.md)）。

**5.2 推薦側は設定ファイルを読まず、ユーザーの状態を保存しない。** 数値も履歴も呼ぶ側から毎回引数で受け取る（契約1（OctantCompass・OctantHarvest → OctantVector）、憲法の原則 3）。履歴から作った好みと実力をプロセスの中でキャッシュするのは構わないが、ディスクに残して正本のように扱わない。生成側が自分の設定と台帳を持つのは構わない。
