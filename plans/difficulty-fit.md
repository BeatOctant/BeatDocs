# 推薦の難易度合わせ

> 固さ: 後から記録する層（[憲法の原則 10](../constitution.md#10-段階と文書の固さ)）。実装済みの仕組みの説明で、正本はコードです。

2026-10-02 作成 · 状態: 実装済み（OctantVector 0.5.0 の `runtime/skill.py` と `runtime/recommend.py`。セッションは OctantCompass の `service.py`）。挑戦の割合と、6 の 1・2（ほかの記録からの補い、初回画面）はまだない（コードに見当たらない）

## 目的

推薦したマップが好みに合っていても、難しすぎたり易しすぎたりすると遊んでもらえません。この文書は、推薦する譜面（マップの難易度）をユーザーの実力に合わせて絞り込む仕組みを決めます。

難しさは 1 本の数値では表しません（決定、2026-10-03）。ゆっくり飛んでくる譜面は密度に関係なく苦手な人もいれば、ゆっくりで高密度の方が得意な人もいます。Easy〜Expert+ を難しさの順ではなく、Tech 譜面・Acc 譜面のような作風で分けるマッパーもいます。そこで、ある譜面がその人にとってどのくらい難しいかは、**譜面の特性（手首の切り返し、速さ、密度、並びの角度、リズムなど）の空間で、その人が得意とする譜面からどのくらい離れているか**で表します。Easy〜Expert+ の名前やマッパーが付けた難易度名は、難しさの判断に使いません。

- 好みの推薦（似ているマップを探す部分）は [契約](../contracts/README.md) の契約1（OctantCompass・OctantHarvest → OctantVector）と [OctantPath の実装構想](octantpath-implementation.md)にあり、この文書は難易度だけを扱います
- 推薦は譜面（`hash` + `characteristic` + `difficulty`）まで指定して返します。関数と API の形は [契約](../contracts/README.md) の契約1（OctantCompass・OctantHarvest → OctantVector）・契約2（DB 生成 ↔ 推薦コア）・契約3（OctantPath ↔ OctantCompass）にあります

## 分かっていること

開発に使った 1 人分のプレイデータと公開データの実験で分かっていることです。数字は OctantVector の[実験ログ](../octantvector/experiments.md)にあり、ここでは結論だけを使います。

- 選んだ難易度の NPS で、クリアか失敗かをかなり見分けられる（exp03）
- 途中終了・失敗したマップと好きなマップの違いは、ほとんどが難易度で、好みの違いではない（exp05）
- 難易度の合う範囲を推薦の順位に足すと少し良くなるが、似ている度合いに混ぜるより、別の項として使う方がよい（exp04、exp05）
- スイングシミュレーションの Pass は、NPS より星（ScoreSaber・BeatLeader）とよく合い、上級者のリプレイとも合う（exp17、exp18。手法は [swing.md](../octantvector/swing.md)）
- 時間帯、曜日、プレイの間隔では変わらず、セッションの中の位置だけで変わる（exp20。「状況による調整」の節）

ここまでの実験は NPS や Pass のような 1 本の数値で測っています。特性の空間での距離が、それらより次のクリア・失敗をよく当てるかはまだ確かめていません（「確かめ方」の節）。

## 役割分担

難易度の値を持っているのは OctantVector の配布 DB で、プレイの記録と設定の正本は OctantPath、それをキャッシュして「今どういう状況か」を知っているのは OctantCompass です（憲法の原則 5・7。2026-10-12 に憲法に合わせて直した）。そこで、計算は OctantVector、何を狙うかの判断と記録は OctantCompass に分けます。OctantPath は DB の中身を知らない（契約1（OctantCompass・OctantHarvest → OctantVector）だけを知る）という契約の方針もそのまま守れます。

| 仕事 | 担当 | 理由 |
| --- | --- | --- |
| 譜面ごとの特性の値（スイングシミュレーションの特徴量、NPS、NJS、Pass、Tech） | OctantVector（配布 DB） | 譜面を解析して DB に入れるのは OctantVector |
| プレイ記録の保存（時刻、譜面、結果、速度などの修飾） | OctantPath（正本）と OctantCompass（キャッシュ） | ユーザー状態の正本は OctantPath（憲法の原則 5・7）。OctantCompass は signal をキャッシュし、OctantVector には履歴として渡す（契約1（OctantCompass・OctantHarvest → OctantVector）） |
| 実力の推定（得意な譜面の集まりと、離れたときのクリアのしやすさ） | OctantVector（`recommend` と `describe` の中） | 特性の値を引くのに DB が要る |
| 狙いの選択（ふつう・挑戦・慣らし、状況による調整、手動指定） | OctantCompass | 設定、時刻、セッションを知っているのは OctantCompass。狙いを選ぶのはスケジューリング（[推薦の定義](recommendation-definition.md)の Q4） |
| 狙いから距離への変換 | OctantVector（`recommend`） | 距離は特性の空間の値で、OctantCompass は計算しない（憲法の原則 4）。狙いは「クリアできる見込み」の尺度で受け取る |
| 絞り込みと難易度の選択 | OctantVector（`recommend`） | 候補ごとに全難易度の値を見る必要がある |
| 表示と手動指定の入口 | OctantPath（MOD） | 画面は MOD |
| 数値の既定値と変更 | 設定 JSON（契約3（OctantPath ↔ OctantCompass）） | 数値はすべて設定 JSON で変える決まり |

## 仕組み

### 1. 譜面の特性

譜面ごとに、次の特性を並べたもの（特性ベクトル）を使います。値は配布 DB の難易度単位の表（契約2（DB 生成 ↔ 推薦コア）の `charts.parquet` と、難易度単位のビュー）から引きます。

| 特性 | 中身 | 使い始め |
| --- | --- | --- |
| 速さ | NJS、スイング数/秒、EBPM | NJS は最初から、ほかは DB に入ってから |
| 密度 | NPS、同時打ち・stack の割合 | NPS は最初から |
| 手首 | 切り返し（リセット率）、ロール角の大きさ、逆手の割合、角度ひずみ | DB に入ってから |
| 並び | 斜め・横・非 45° 角の割合、移動距離、ジャンプ、クロスオーバー | DB に入ってから |
| リズム | 間隔の種類のエントロピー、裏拍・3 連符の割合、間隔の変化率 | DB に入ってから |
| 体の動き | プレイに関わる壁・爆弾の頻度 | DB に入ってから |

特性の中身と計算方法は [swing.md の特徴量](../octantvector/swing.md#特徴量swing_flow)にあり、どの特性を使うかと特性ごとの重みは設定で選べます（全難易度の特性が DB に入ったら、上の表の全特性を重み 1 で使う予定）。各特性はプール全体の分布で標準化してから距離を測ります（単位の違う値を並べるため）。

- Pass と Tech は特性の 1 つとして使い、表示にも出しますが、これだけで難しさを決めることはしません
- `swing_flow` は Standard の全譜面を 1 譜面ずつ計算し、譜面単位のビューとして DB に入ります（配布はまだ）。DB に入るまでは NPS と NJS の 2 つで同じ仕組みを動かします
- 特性はプレイスタイルごとに別のものとして扱い、違うプレイスタイルの譜面とは距離を測りません（[憲法](../constitution.md)の原則 2）。スイングシミュレーションは Standard 用なので、ほかのプレイスタイルの特性は NPS・NJS と `chart_patterns` から始めます

### 2. 実力の推定

実力は「得意な譜面の集まり」と「そこから離れたときのクリアのしやすさ」で表します。

- **プレイスタイルごとに作る**: 得意な譜面の集まりと離れる向きは、プレイスタイル（Standard、OneSaber など）ごとに作ります。あるプレイスタイルの記録が少ないときに別のプレイスタイルの記録で補ってよいかは、確かめてから決めます
- **得意な譜面の集まり**: 最近クリアした譜面の特性ベクトルの集まりそのもの。ある譜面の「その人にとっての難しさ」は、この集まりの近いもの（設定の k 件）までの距離の平均です。得意な譜面が 1 か所にまとまっていない人（Tech 譜面と Acc 譜面の両方が得意など）でも、どちらかに近ければ近いとみなせます
- **離れる向き**: 同じ距離でも、離れる向きで失敗しやすさが違います（開発に使った記録では NJS が遅い向き）。失敗した譜面の特性から、クリアと失敗を分ける向きを学び、その向きの距離を重く数えます。易しすぎる向きに離れた譜面も「合わない」ので、距離は向きにかかわらず数えます。やり方（OctantVector 0.5.0、#54 の実装に合わせて記録。推測で、確認待ち）: 向きは特性ごとに、一番近い得意な譜面より上か下か。最近のプレイのロジスティック回帰で、向きごとに落ち方（距離あたりのクリアのしやすさの下がり方）とその標準誤差を出す。設定の重みは全向きの平均の落ち方にあたる（上がる向きは 0 と数える）。「落ち方 − 標準誤差」がその平均より速い向きは ((落ち方 − 標準誤差) / 平均)^2 倍重く数え、ほかは設定のまま。`describe` の `weakDirections` はこの向きと倍率
- **クリアのしやすさ**: クリアと失敗を、この距離で説明する曲線（ロジスティック回帰）。距離がいくつならどのくらいクリアできるかが分かり、狙う位置（下の 4）に使う
- 使うプレイ: 速度 1.0 で、ノーフェイルなどの難しさを変える修飾がないもの。途中終了は数えない（好みの判定ルールと同じく、理由が分からないため）
- 「最近」の範囲: 直近の件数か日数で区切る。実力は伸びるので、古いプレイが基準を引き下げないようにする。苦手な向きの学習では、得意な譜面の集まり（`strongRecentClears`）の一番古いクリア以降のプレイを使い、それより少なければ全部。クリアできる見込みの曲線は今も全プレイを使う（曲線も範囲を切るかは決めること。OctantVector 0.5.0）
- 記録が少ないうちは、離れる向きは学ばず（全特性を同じ重みで数える）、ScoreSaber / BeatLeader のローカル記録とゲームの `PlayerData` のクリア記録で集まりを補う（未実装）。それもなければ下の 6
- 離れる向きの学習は 1 人分のデータで行うので、学んだ重みは記録の件数に応じて既定の重みに寄せる（[personal-data-overfitting.md](personal-data-overfitting.md) の縮め方と同じ考え方）。n を最近のプレイ（クリアと失敗）の数、n0 を `params` の `directionShrinkPlays` として、n / (n + n0) の割合で学んだ重みに寄せる（OctantVector 0.5.0）

### 3. 絞り込みと難易度の選び方

推薦の候補ごとに、全難易度の中から狙う距離に一番合う難易度を選び、その難易度で絞り込みと順位付けをします。Easy〜Expert+ の並び順は使いません。

1. **選ぶ**: マップの各難易度について、その人にとっての距離を出し、狙う距離に一番近い難易度をそのマップの推薦難易度にする
2. **絞り込む**: 選んだ難易度でも狙う距離から許容幅より外れるマップは候補から外す（「話にならない」譜面を確実に出さないため）
3. **並べる**: 残ったマップは好みのスコアに、狙う距離からのずれに応じた小さな減点を足して並べる（今の `beta` の項）

絞り込みが強すぎて候補が足りないときは、許容幅を設定の上限まで段階的に広げ、それでも足りなければ足りないまま返します（遊べない譜面で埋めないため）。

### 4. 狙う位置

狙いは、OctantCompass が推薦の枠と状況から名前（ふつう・挑戦・慣らし）か「クリアできる見込み」の目標で選び、OctantVector が下の表のように距離に変えます。枠そのものは[実装構想の「似ている」の分け方](octantpath-implementation.md#似ているの分け方)にあります。

| 狙い | 距離 | 使う枠 |
| --- | --- | --- |
| ふつう | 得意な譜面どうしの距離と同じくらいまで（クリアした譜面の距離の設定のパーセンタイル以内） | 曲が似ている、ジャンルが近い、譜面が似ている |
| 挑戦 | それより少し遠く、クリアのしやすさが設定の値（例: 半分くらいクリアできる）になる距離。苦手な向きに離れた譜面も含む | 難易度が合う（の一部） |
| 慣らし | 得意な譜面のすぐ近く | 状況による調整で使う場合だけ |

- OctantVector 0.5.0 は、ふつうの狙う距離を得意な譜面どうしの距離の中央値にし、`normalPercentile` は曲線がないときの挑戦の位置（そのパーセンタイルにばらつき 1 つ分を足した距離）にだけ使う（`runtime/skill.py` の `target`）
- OctantCompass は `auto` で挑戦を選ばない。挑戦は MOD が明示したとき（手札 `challenge`）だけ（2026-10-12）

挑戦を混ぜるのは、得意な譜面の近くだけを出し続けると、苦手を広げられず、実力が伸びても推薦が追いつかないためです。挑戦の譜面は失敗しても好みの判定に悪く効かないので（失敗はプレイ回数に数えるだけ）、嫌いと誤解する心配はありません。

### 5. 状況による調整

時間帯、曜日、プレイの頻度、セッションの序盤・中盤・後半で狙う難易度を変えるべきかを、開発に使った 1 人分のプレイ記録で確かめました（exp20。数字と手順は[実験ログ](../octantvector/experiments.md)）。効いていたのはセッションの中の位置だけなので、調整はそれ 1 つにします。

- 序盤は易しめを選び、合わなければすぐやめている。後半は難しいものを選び、同じ難しさでも失敗しやすい
- 疲れの積み重なり、時間帯、曜日、直近の頻度は効いていない。長い休みは記録が少なすぎて分からない

この結果から、次のように決めます。

| 状況 | 調整 | 理由 |
| --- | --- | --- |
| セッションの最初の数プレイ | 狙う距離を縮める（慣らしの狙い） | 序盤は易しめを選び、合わないとすぐやめる |
| それ以降 | ふつうの狙いは広げない。挑戦の狙いは序盤には出さない | 後半は同じ難しさでも失敗しやすい |
| 時間帯、曜日、頻度、休み | 調整しない | 差が見えない。休みは記録が少なすぎるので、データがたまったら確かめ直す |

セッションは OctantCompass が判断します。前のプレイの終わりから設定の時間以上空いたら、新しいセッションとして数え直します（ゲームの起動は使わない。[契約3](../contracts/mod-api.md)、2026-10-12）。セッションの中の何プレイ目かは、OctantCompass が保存したプレイ記録の時刻から数えます（OctantVector はセッションを知りません）。

exp20 は NPS と NJS の帯で測りました。距離に置き換えたときの慣らしの縮め方は、同じ記録で確かめ直します。過去のクリアから作った帯には、次に遊んでクリアした譜面が名目より入りにくかった（実験ログ）ので、決まった範囲の外を一律に捨てず、距離でも許容幅を持たせた絞り込みと減点の組み合わせ（3 の手順）にしています。

### 6. 記録がないとき

初めて使うときなど、得意な譜面の集まりを作れるだけのクリアがないときは、次の順で決めます。

1. `PlayerData` のクリア記録（OctantPath が初回に取り込む `imported_play` の `cleared`）で集まりを埋める。自分の素のクリアを先に入れ、残りの枠だけを、プレイ回数の多いものから埋める。自分のクリアが増えると、取り込んだものは回数の少ないものから枠を出る（2026-10-24。ScoreSaber / BeatLeader のローカル記録はまだ読まない）
2. それもなければ、MOD の初回画面で「普段楽に遊べる譜面」を数件選んでもらい、それを仮の集まりにする（Easy〜Expert+ の名前では聞かない。名前の付け方がマッパーごとに違うため）
3. 選ばれなければ、どの譜面も距離を測れないので難易度では絞らず、クリアが設定の件数たまったら推定に切り替える

### 7. 表示と手動指定

- MOD の推薦一覧には、選んだ難易度、その人にとっての距離、狙い（ふつう・挑戦）と、一番近い得意な譜面を出す（「この譜面に近い」と分かるように）
- 実力は `/v1/profile` で、得意な特性と苦手な向き（例: NJS が遅い譜面）として表示する（契約3（OctantPath ↔ OctantCompass））
- 推薦要求の難易度は `auto` か明示で、明示なら狙い（ふつう・挑戦・慣らし）か距離をユーザーの指定どおりに使い、状況による調整はかけない

## 設定

数値は契約1（OctantCompass・OctantHarvest → OctantVector）の `params` で受け取り、OctantPath の設定 JSON（`Beat Saber/UserData/OctantPath/`）から変えられます。既定値の正本は、難易度の項目が OctantVector の [`common/params.py`](https://github.com/BeatOctant/OctantVector/blob/main/src/octantvector/common/params.py) の `DEFAULTS`、セッションの区切り（`sessionGapMinutes`）と慣らしのプレイ数（`warmupPlays`）が OctantCompass の [`service.py`](https://github.com/BeatOctant/OctantCompass/blob/main/src/octantcompass/service.py) です。項目の意味は [params のスキーマ](../contracts/schemas/engine-runtime/params.schema.json) と[契約3](../contracts/mod-api.md)にあります。挑戦の割合（案は難易度が合う枠の半分）はまだ設定にありません（[open.md の難易度合わせ](../open.md#難易度合わせ)）。

k、パーセンタイル、慣らしの距離は仮の値で、下の「確かめ方」で決めます。実力に使う最近のクリアの数（`strongRecentClears`）は、exp20 の 1 人分の記録から決めたものです。`minClears`（50）は裏づけのない仮の値で、取り込んだクリアも数えるので、PC では多くの人が最初から効きます。使う人が増えたら、台帳の数字で見直します。

## 確かめ方

- **実装前**: 開発に使ったプレイ記録を時刻順に流し、その時点までの記録で実力を作って、次のプレイがクリアだったか、ふつうの狙いの範囲に入っていたかを見る（未来の記録は使わない）。比べるのは、今の 1 本の数値の帯（NPS、Pass）、NPS と NJS の帯、特性の距離（向きの学習なし・あり）。距離がよく当てられなければ、帯に戻すか、特性を絞る。特性の選び方、k、パーセンタイル、最近のプレイの範囲もこれで決める。決め方は [personal-data-overfitting.md](personal-data-overfitting.md) のとおり（選ぶ用と確かめる用を時刻で分け、差が区間に収まるなら簡単な方）
- **使い始めてから**: 台帳に入った枠と狙いごとに、クリア・失敗・途中終了の割合と「残す」の割合を数える。ふつうの狙いで途中終了が多ければ距離の測り方がずれている、挑戦で失敗ばかりなら狙いが遠すぎる、と分かる
